# 多智能体协作编排

把委派当作提高速度、质量或主上下文稳定性的手段，不把派生数量当作成果。主智能体始终对用户意图、权限、关键取舍和最终交付负责。

## 1. 判断是否委派

满足以下任一条件时优先委派：

- 至少两条工作流可以独立推进；
- 宽搜索、跨模块探查或多方案比较明显受益于并行；
- 支线会产生大量中间信息，可能污染主上下文；
- 结论需要独立验证、反方审阅或与作者隔离的验收；
- 用户明确要求子智能体、委派或并行 Agent 工作。

任务很小、高度耦合、关键步骤严格串行，或协调成本可能高于收益时，由主智能体直接完成。不确定时，先派一个范围小、只读、可快速验收的探查任务，再根据结果决定是否扩展。

## 2. 绘制任务地图

委派前先形成简洁任务地图。为每个子任务明确：

- 目标和它将消除的不确定性；
- 必要上下文与必须读取的来源；
- 范围边界、禁止事项和授权限制；
- 允许使用的工具；
- 具体交付物与完成条件；
- 上下游依赖；
- 文件、组件或工作树所有权。

只传完成任务所需的上下文。独立验证时传原始材料和验收目标，不泄露预期答案、已有诊断或倾向性结论。

## 3. 划分并发与所有权

- 优先拆分互不重叠的只读任务。
- 共享工作区中的并行编辑必须按互不重叠的文件、组件或工作树划分所有权。
- 明确告知编辑型子智能体：它并非独占代码库，不得回退他人改动，发现并行变化时应主动适配。
- 发现范围重叠、同一文件竞争或隐含串行依赖时，立即重划边界或改为串行。
- 并发数量以当前独立工作流数量为上限；不要为了占满槽位拆出没有独立价值的任务。

## 4. 下发任务

优先复用已经掌握相关上下文的子智能体，不为同一工作重复派生。根据宿主提供的角色和工具选择合适执行者：代码库定点探查使用只读探索角色，明确文件所有权的实现使用执行角色，独立审阅使用审阅角色。

任务说明应短而完整，至少包含目标、边界、来源、交付物和完成条件。子智能体不得获得超出当前用户授权的权限；需要用户确认、外部发送或高风险操作时，由主智能体保留决策和动作责任。

## 5. 并行推进与监督

派出任务后，主智能体继续推进不依赖子结果的主线，不原地等待。按宿主能力查看状态、等待更新、补充指令或中断错误方向。

对子智能体的过程管理遵循：

1. 迟缓或输出不足时，先检查它已完成什么、卡在哪里；
2. 优先给原智能体补充上下文、缩小范围或要求从已有进度恢复；
3. 只有任务已终止、无法恢复或方向确实错误时才替换；
4. 不为同一失败无界重试，也不派新智能体重复尚可恢复的工作。

## 6. 核验并整合

不要把子智能体报告直接当作事实。整合前：

- 检查引用、文件、命令输出或原始材料是否支撑结论；
- 对照各子任务边界，确认没有遗漏关键消费者、场景或依赖；
- 识别结果之间的冲突，回到证据解决，不按多数票决定；
- 对代码改动检查实际 diff、测试结果和文件所有权；
- 明确哪些结论已证实、哪些仍是假设或受限于未覆盖范围。

主智能体据此形成统一判断和最终交付，不把多份子报告简单拼接给用户。

## 7. 停止委派

满足任一条件时停止新增委派：

- 已有证据足以完成用户目标；
- 剩余工作需要统一判断或高度耦合实现；
- 新增子任务不会改变决策，只会重复已有证据；
- 协调成本或等待成本已超过预期收益。

任务结束时确认所有编辑均已纳入主线判断，未完成或被中断的子任务不会留下被误认为有效成果的文件或状态。
