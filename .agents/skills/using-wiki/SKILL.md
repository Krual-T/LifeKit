# Using Wiki

## 记忆机制

`wiki/` 是记忆数据库，保存长期和短期记忆；`AGENTS.md` 提供记忆索引，“最近”通常指向近期相关的短期记忆，也可以索引常用的长期记忆。入口只保存主题提示和路径。索引之外的记忆仍在 Wiki，可以检索；移除入口不删除原文。

保存的依据是以后是否需要回想。经历、感受、灵感和临时状态都可以记录，不要求有待办或成为长期结论。页面和目录按独立回看、检索与维护的需要组织，长短期记忆不需要分别放置或相互迁移。

存储遵循标准 [OKF 0.2](references/okf-0.2.md)，编辑页面时按需查阅。目录、类型和正文结构按内容选择，普通记忆不必套用任务交接模板。项目权限和版本管理规则见实例根 `AGENTS.md`；新实例从 [AGENTS 初始化模板](../../../.codex/templates/AGENTS.ini.md) 建立这些规则。

## 查

有明确路径（包括 AGENTS 近期入口）就直接读原文；没有路径时，默认用 **`wiki-retrieval`** 找页面：

```bash
wiki-retrieval query "需要回想的主题" --wiki-root wiki --include-draft --limit 3 --format text
```

根据上下文选择候选，读取问题所需的原文。以下命令中的路径换成实际查询命中的页面：

```bash
wiki-retrieval get notes/example.md --wiki-root wiki --level l2 --format text
```

工具做本地词法检索，查询时自动同步派生索引；`--include-draft` 让未整理完的记忆也能被找到，追查废弃记录时另加 `--include-deprecated`。示例中的结果数量可按问题调整；候选用于定位，结论回到原文及其状态、日期和来源。必要时调整关键词、沿 `wiki/index.md` 浏览或用 `rg` 补查。

## 增删改与整理

1. **写入时同步整理。** 先查已有主题。新信息进入时，判断它是补充、替代还是与原记录冲突：补充内容合入对应位置，有明确依据的变化更新原状态，未解决的冲突保留各自来源与适用范围。同一事实只保留一份权威记录，其他页面通过链接引用。
2. **明确当前与历史。** 描述当前情况的内容应反映最新已确认状态，并保留必要的确认日期。被替代的信息按回顾价值压缩为历史，说明后续变化；原本错误的信息直接纠正。信息是否失效依据新证据和适用条件判断，不能仅凭记录日期较早判定。
3. **按独立主题组织页面。** 同一项目下需要分别检索、更新或回顾的内容，可以独立成页。当多个主题混杂，或当前结论被大量过程记录淹没时，主动拆分、合并和重写，保留必要的背景与关联链接。
4. **按内容递归组织目录。** 相关页面形成自然分组时，主动建立子目录；对子目录继续采用同样的判断。层级服务于查找与维护，不预设固定深度，也不按文件数量机械拆分。
5. **保留有价值的记忆与依据。** 经历、感受和决定变化按回顾需要保留时间线。已有独立记录的详细实验、执行日志和实现过程，Wiki 保存其结论、关键理由、必要背景与来源链接。整理范围以当前主题及直接相关页面为主，同时修正引用和索引。

删除时按目标范围处理内容或整页；删除目录时保留其中仍需使用的内容。未访问、退出近期索引和“先放着”都不表示忘记。当前文件删除后，Git 历史仍可能保留旧内容。

移动、合并或删除时，用 `rg` 按旧路径和文件名查引用，修正入链及页面自身的相对链接、来源路径；清理无用目录及其生成导航。涉及 AGENTS 入口时用下面的 `remove` 移除旧入口，仍需近期索引则用 `add` 加入新路径。

## 索引维护

新增或更新记忆后，判断近期是否可能再次用到；值得保留近期入口时，用 `wiki-index add` 加入或更新顺序。保存到 Wiki 不要求同时进入近期索引。

以下命令在项目根运行，路径相对 `wiki/`。`add` 将页面加入或移到近期索引前部；`remove` 只移除入口，可一次传入多个路径。两者都会同步导航：

```bash
wiki-index add notes/example.md
wiki-index remove notes/example.md
```

实际使用且仍有近期复用价值时更新顺序，不再相关时移除。容量与固定规则沿用 AGENTS.md，`add` 超出容量时只淘汰最冷的非固定入口，不删除 Wiki 正文。索引会过时，不代表记忆失效；当前不设固定天数的自动过期。工具不替助手判断哪些记忆重要，也不编辑、移动或删除记忆正文。当前工具需要入口对应页面有单行 `title` 和 `description`，用于生成导航。

已信任并加载项目 `.codex/config.toml` 中 Wiki Hook 的 Codex 宿主，会在当前会话工作树的 `apply_patch`、`Bash` 完成后检查实际文件并同步导航与检索。无变化时静默；实际同步后提供简短结果，生成导航时附路径，失败时给阶段和错误。首次安装与启用见[项目 README](../../../README.md#初始化)。实例是否已加载 Hook 需在当前宿主核实。

未启用 Hook、通过其他工具或跨工作树写入、外部编辑，以及自动同步失败时，显式执行统一入口；在目标工作树根目录可以省略 `--project-root`：

```bash
wiki-index ensure --project-root <目标工作树绝对路径>
```

`ensure` 复用导航生成、完整 OKF 校验和检索同步，成功时退出码为 0，JSON 返回 `ok=true`、`fresh=true` 和生成导航路径。锁等待和子进程共用默认 20 秒预算，可用 `--timeout` 调整；并发输入变化最多补做一次。失败时返回非零退出码及已生成的导航路径，检索若已发布则保留，不声称两种输出可以一起回滚。

模型收到并处理编辑工具的 Hook 结果后，再审阅、暂存和提交本次正文与导航。若在同一条 shell 命令或同一个 code mode 脚本中连续编辑并提交，必须在暂存前显式执行 `ensure`，检查退出码为 0 后再继续。Hook 的错误只补充模型上下文，不会拒绝原工具的 Promise；不能把工具执行成功当成同步成功。

生成的 `index.md`、AGENTS 的 `memory-recent` 区域和 `wiki/.okf/` 派生索引由工具维护；失败时按错误修正，不能将尚未同步的索引当作最新结果。

`wiki-index` 对应本 skill 的 `scripts/wiki_index.py`；未安装命令时可用 `uv run --script .agents/skills/using-wiki/scripts/wiki_index.py <操作>`。在项目根初始化后，将实例 `.venv/bin` 加入当前进程 PATH，使用其中的命令链接。`wiki-retrieval` 的安装入口见[工具说明](../../../projects/okf-retrieval/README.md)。

Hook 适配器为 `scripts/wiki_sync_hook.py`，只监听 `PostToolUse` 的 `apply_patch` 和 `Bash`，依据会话 cwd 与自身所属 Git 工作树限定范围，不解析命令关键词，也不检查工具是否成功退出。它依赖 PATH 中的 `python3`、`git`、`uv`、`wiki-retrieval`；使用离线 `uv run --script`，首次启用前需要准备已有脚本的 PyYAML 依赖缓存。Hook 总超时为 30 秒。通过 Codex `/hooks` 信任该项目的确切配置后才能自动运行；关闭时移除这一项配置，继续显式执行 `ensure`。不要为此关闭整个宿主的 Hook 信任机制。
