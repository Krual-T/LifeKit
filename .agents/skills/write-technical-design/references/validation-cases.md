# 行为验收场景

仅在维护 Skill 或审阅角色时使用。静态格式检查不能证明审阅质量。

## 方法

在 Git 忽略的隔离目录或临时目录准备最小仓库与文档。给新子 agent 只提供角色协议、原始文档、仓库路径和必要需求；不要传入下方预期、作者结论或缺陷标签。保留测试产物在忽略目录，不提交原始 agent 日志。

主 agent 将实际发现与事先明确的预期比较；不能将针对示例的成功宣传为真实项目全面验收。先修正实际失败的规则，再用不同案例前向验证。

## 场景 A：已有能力与新增对象

- 原始仓库：已有版本条件更新和修订记录事务操作，有一个真实调用者和相关测试。
- 待审方案：新增执行相同职责的类、额外审计表、只有一个调用者且无独立约束的透明包装层，并将先查版本再无条件更新写成无保护步骤。
- 需求：保存及修订记录必须原子提交，拒绝旧版本覆盖；没有额外审计留存要求。
- 预期：通过实际源码指出可复用操作；识别并发漏洞；裁决移除包装层和新表；给出基于已有操作的单一目标方案。结论须有路径或符号依据，不能仅泛称过度设计，也不能把这些技术选择上抛给用户。

## 场景 B：简洁不等于盲删

- 原始仓库：事务边界保证两项写入原子提交，唯一约束防止重复；另有同名但绕过权限或不满足事务契约的工具方法。
- 待审方案：直接复用符合契约的入口、保留必要事务与约束；以短文而非完整九章说明场景和错误语义。
- 预期：认可合理裁剪；保留必要约束，不因同名或代码短而误用工具方法；明确不采用更短但破坏契约的替代方案。

## 场景 C：证据不完整

- 输入一份可读文档但目标仓库路径不可访问，或关键外部消费者无法核实。
- 预期：完成文本部分，给总体“证据不足”；不伪造路径、不宣称不存在复用能力，也不把未发现调用者直接等同于可删。

## 场景 D：技术裁决与价值取舍

- 原始仓库：两种内部实现都能满足已知契约，其中一种增加配置开关、适配接口和备用路径，另一种直接扩展现有操作且可逆。
- 待审方案：把两种实现、是否保留开关及是否预建备用路径全部列为用户待选项；需求只要求删除后正常读取不可见，没有说明历史数据的长期政策，当前实现也无需主动删除历史。
- 预期：审阅者直接裁决采用更小的现有操作扩展，删除开关、适配接口和备用路径，不要求用户选择内部实现；历史政策不影响当前最小行为时也不上抛，只在方案将执行不可逆历史删除或当前验收明确要求确定政策时才交给用户。

## 写作验收

使用一个新的小功能任务，给需求、仓库和 Skill 路径，让 agent 起草文档并独立审阅。检查能否从场景讲清方案、是否先调查已有实现、是否区分现状与提议、是否避免全量类函数清单、是否对关键对象与替代方案给出具体依据。不可派生时应报告独立审阅未完成。

## 配置验收

- 运行 skill-creator 自带 quick_validate.py，校验 Skill frontmatter；解析 UI YAML 和角色 TOML，检查名称及必填项。
- 用本机 Codex 的只读发现机制确认命名角色是否被加载；如无法观测，明确配置落盘但原生加载未验证。
- 当前派生工具不支持角色参数时，将 TOML 的 developer_instructions 原文交给子 agent 验证行为；这只能证明协议委派，不证明命名角色启动或沙箱生效。
