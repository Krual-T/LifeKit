# 功能技术设计与独立审阅

让未参与设计、懂业务且具备基本技术背景的人，不读源码也能解释功能如何实现、为什么成立、失败后留下什么，以及实现时哪些规则不能改。

本 Skill 负责技术结构与工程判断；同时读取并复用 [ai-writing-rules](../write/ai-writing-rules/SKILL.md) 的 Technical profile，避免复制通用写作规则。

## 入口与边界

- 区分起草、修改、只读审阅。只读审阅不改原文；写作任务默认包含独立审阅，用户明确排除时除外。
- 从当前上下文确定需求来源、目标仓库绝对路径、基线分支或提交、设计文件及目标读者。先查可发现信息，仅对影响方案且无法查明的缺口询问用户。
- 需求是输入：引用功能、业务规则和质量约束，不重做需求分析。未决业务语义只有确实改变当前外部行为且无法延后时才标成待确认；不能以技术选择偷偷补齐需求，也不为当前无需承诺的未来政策打断用户。
- 目标仓库可能不同于 Skill 所在仓库。分别读取目标仓库根目录到相关模块的 AGENTS.md，检查 Git 状态；既有未提交修改保持原样，证据说明来自提交还是当前工作树。
- 只修改获准的设计文档和约定审阅产物，不顺手改应用代码、执行 DDL、安装依赖、修改线上配置或发送外部内容。
- 仓库不可读时，可以形成文档草案或做文本审阅，但明确“仓库复用未核实”，不得给出完整通过结论。

## 决策权与上抛边界

- 默认由 Agent 完成技术裁决，不把“删除／修改／新增”、内部结构或实现手段整理成菜单交给用户。作者可在内部比较候选，但交付一份已经取舍的方案。
- 复杂度本身是持续成本。新增对象、状态、副本、依赖或扩展点必须由当前消费者、已知约束或可触发故障举证；“将来可能需要”或理论风险不能单独成立。证据不足时默认不新增，优先复用、内联、合并或留到真实需求出现。
- 只有无法由需求、仓库事实和既定约束推导，并且确实阻碍当前方案的业务含义、风险偏好、不可逆迁移、外部承诺或权限扩张才交给用户。能够保持现状或不扩大承诺而延后的决定直接延后。提问时说明技术上已经确认的部分、剩余价值取舍及其后果，不把可自行调查或可逆的实现选择伪装成用户决策。
- 证据冲突或关键资料缺失时，先继续调查；仍不能成立则明确结论边界并选择不扩大承诺的可逆方案。不能用增加兼容层、开关、包装层或多套路径来掩盖未知。

## 写作流程

### 1. 先找已有实现

用 `rg --files` 定位入口、模块、测试、迁移和依赖声明，再按功能语义、相关符号和调用者搜索；优先读一条真实执行路径，不做无边界全库扫描。

确认可复用能力的实现、调用者、契约、权限、事务或生命周期约束，不能凭名称相似断言可以复用。记录“直接复用／扩展现有／新增／替换”的选择及路径、符号依据；查不到时注明搜索范围，不把一次零命中写成全仓库不存在。

### 2. 先走通场景，再划分结构

1. 用一段话给出实现策略、改动边界和明确不做的事情。
2. 选代表性场景，从触发到完成走通，交代参与方、顺序、分支、数据变化及用户可见结果。
3. 据此确定模块职责、数据所有权、依赖方向和关键操作契约。
4. 补充真实可触发且影响设计的异常、并发、重复调用、部分成功和恢复路径。
5. 只对仍有歧义的关键内部逻辑补对象定义或伪代码，再从契约与不变量推导验证场景。

HLD 解释边界、职责、协作策略和关键取舍；LLD 明确操作语义、数据约束、控制顺序和关键内部设计。允许往返迭代和合并成一份文档。

### 3. 按读者的问题组织文档

使用 [可裁剪模板](references/document-template.md)。小改动合并章节，不保留空标题，不要求图种齐全；重要语义不能因为裁剪而消失。

| 读者的问题 | 必须表达的内容 | 推荐表达 |
| --- | --- | --- |
| 由谁完成？ | 职责、非职责、所有权、依赖 | 结构图与简短职责表 |
| 怎样完成？ | 关键场景执行顺序与分支 | 时序图或编号步骤 |
| 遵循什么约定？ | 输入输出、前置条件、成功保证、副作用、失败语义 | 操作契约 |
| 什么会变化？ | 对象关系、持久化、状态、不变量及保证机制 | 数据表、ER 图或状态图 |
| 出问题怎么办？ | 并发、事务、重试、恢复与最终状态 | 异常场景说明 |
| 为什么这样做？ | 仓库复用、必要性、替代方案、代价与假设 | 取舍说明 |
| 怎样证明成立？ | 可观察结果、验证场景和必要的迁移发布安排 | 场景与预期结果 |

- 每张图只回答一个问题；使用稳定术语、标明参与方和箭头含义。正文先讲业务含义，再展示类型、签名或 DDL。
- 接口成功必须区分“已接收／已持久化／已处理完成”。写明失败是否可能已经产生副作用，不能把网络超时直接等同于服务端失败。
- 数据结构之外写出始终成立的不变量，以及负责保证它的约束、事务或其他实际机制。
- 图、文字、接口表与伪代码相互引用，每项关键事实保留一处权威定义；不要维护几份重复逻辑。
- 普通访问器、框架样板和容易改变的私有细节留给编码。只有不同理解会改变行为、边界、一致性或主要质量约束时才展开。

### 4. 对方案做减法

对本设计提出的每个新增或修改对象追问：谁实际使用它？它承担哪个当前职责或约束？删除、内联、合并或复用已有实现后，具体会损失什么？对象包括方法、类、接口、字段、表、索引、迁移、事件、配置、依赖和后台任务，不限于面向对象代码。

将理由写在相关定义或取舍旁；只有复杂改动才使用简短对象表，不另外维护全仓库台账。无关存量对象不纳入本次删减，也不要为了审阅而先枚举尚未设计的全部内部函数。

优先尝试在已有流程里小改、复用已有抽象、减少状态和数据副本。不能为未知未来消费者添加通用框架、开关或包装层；也不能以“行数少”为由删除真实权限、事务、兼容或故障恢复机制。

对最影响结构的决策比较最有希望的更简单方案（包括不新增组件），说明当前约束下为何更好或不适用。没有更优替代可以保留原案，不为展示反省而凑多个方案。

比较是内部推理，不要求把所有被否决方案呈现给用户。文档只保留最终选择、必要依据，以及确实会影响后续实现或维护的关键取舍。

### 5. 独立审阅与修订

审阅角色的唯一行为定义是 [technical_design_reviewer](../../../.codex/agents/technical_design_reviewer.toml) 中的 `developer_instructions`；`agents/openai.yaml` 只是本 Skill 的 UI 元数据，不是子 agent 配置。

1. 保存可读取的文档快照，或向子 agent 提供完整待审文本；审阅期间主 agent 不同时修改该快照。
2. 若当前宿主支持选择命名角色，调用 `technical_design_reviewer`。如果派生工具没有角色参数，读取上述 TOML，将 `developer_instructions` 原文与必要输入交给新的独立子 agent；如实说明这是协议委派，而非已验证原生角色加载。
3. 委派包只包含：文档绝对路径或全文、目标仓库绝对路径、基线及工作树范围、需求来源、适用约束、审阅范围，以及“只读、不修改外部状态”。不要提供作者自评、期待结论或疑似问题清单来引导答案。子 agent 直接读原始证据，不依赖作者的检索结论。
4. 子 agent 在独立上下文中审阅；主 agent 可并行整理交付说明或查不重叠资料，不重做相同审阅。不支持子 agent 时标记独立审阅未完成，可以自审但不能冒充独立验收。
5. 审阅者不是意见提供者，而是只读裁决者：对可由证据推导的技术选择给出一份可直接应用的删减后方案或精确修订，不把多个等价实现继续上抛。只有命中本 Skill 的上抛边界时才列用户必须决定的事项。
6. 主 agent 逐条核对证据并直接修正文档。与审阅者意见不一致时回到需求或代码事实自行裁决，记录拒绝依据；除非触及上抛边界，不让用户充当两个 Agent 之间的仲裁者。
7. 使用原审阅者复核受影响章节及关联契约，不无限重跑全文。存在阻断项或关键证据不足时保留未通过状态；清楚区分初审结论与修订后结论。

## 交付与停止标准

交付经过裁决和修订的设计文档、独立审阅结论，以及真正无法推导的未决事项；记录审阅所针对的版本或快照。不要把已由 Agent 解决的中间争议和候选菜单转嫁给用户。默认将精简审阅结果留在对话，目标项目要求归档时再保存单独报告。

停止细化的条件：实现者不再需要自行决定关键外部行为、跨模块语义和一致性规则；审阅者能判断正常及失败路径是否成立；剩余选择局限于易改的内部实现。只能靠原型或测试消除的不确定性转成具体验证任务，不靠继续加文字消解。

维护本 Skill 时，用 [行为验收场景](references/validation-cases.md) 做范围明确的前向验证；普通写作不加载这份维护资料。
