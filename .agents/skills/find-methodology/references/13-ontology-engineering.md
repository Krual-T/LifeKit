# 本体论（本体工程）

把一个领域中“有哪些东西、分别是什么意思、彼此如何关联、哪些规则必须成立”明确写出来，形成可共享、可验证的概念模型。这里采用知识工程中的 ontology 含义；具体模型服务于当前用途，并随真实案例修订。

## 适用场景

适合梳理业务术语、设计分类体系或知识库、建立实体关系模型，以及重构概念混杂的类型与数据库结构。对象、关系和约束已经清楚的简单 CRUD，直接实现即可。

先明确模型必须回答的问题，再决定需要哪些概念、关系和约束。TypeScript、SQL 或知识图谱是后续表达选择。

## 输入与参与范围

输入包括用途、必须回答的问题、现有术语或实现，以及真实案例和合法反例。

独立使用时，按问题组织概念模型并完成实例验证。嵌入技术设计、知识整理或数据建模流程时，复用已有定义和材料，提供当前需要的概念、关系与约束，由原流程决定工程实现和交付结构。

## 七步用法

沿用 Noy 与 McGuinness 的七步框架，可在步骤之间往返；以下具体判断包含对用户所提供工程材料的整理。

1. **确定领域与范围。** 用一句话写清用途、使用者和维护者，列出模型必须回答的“能力问题”（competency questions）及范围外事项。问题数量按任务决定，每个问题应能对应所需信息和预期答案。
2. **检查已有模型。** 查现有术语表、类型定义、数据库和适用的领域标准，比较概念含义与约束。能复用则复用，有明确缺口再扩展；名称相同仍需核对语义。
3. **列出重要术语。** 从真实材料提取对象、属性、关系、状态及具体实例，标出同义词、歧义和待确认含义。先收集，再归类。
4. **定义概念与分类。** 给核心概念写定义、例子和反例。用“每个 A 都是 B”判断子类关系；拥有、参与、组成等另建关系。同一对象可能同时具备多个角色，只有业务上互斥的类别才声明互斥。分类深度由区分用途决定。
5. **定义属性与关系。** 明确属性属于什么对象，关系连接什么对象、方向是什么，以及是否随时间变化。只有全部实例都适用的属性才上提到共同父类。关系若带角色、有效期等自己的属性，可建为关联对象。
6. **定义约束。** 写清必填性、值类型、取值范围、单位、唯一性、基数和跨字段规则。区分未知、不适用与确实为空；明确规则来自领域事实、业务政策还是当前实现假设，以及由哪一层保证。
7. **用实例回答问题。** 放入有代表性的真实实例，逐个回答第 1 步的问题。遇到不适配，先判断是数据错误、定义错误还是范围遗漏，再修订。保留合法的反例，用它检验模型是否过度限制现实。

七步框架来源：[Ontology Development 101](https://protege.stanford.edu/publications/ontology_development/ontology101-noy-mcguinness.html)。

## 产出与完成条件

产出范围与能力问题、概念模型、关系与约束、实例检验结果和待确认项。模型能够回答范围内的问题，代表性实例与合法反例得到处理，剩余假设及其影响明确时完成。

## 判断模型是否合适

Gruber 的五项设计准则可用于取舍：

- **清晰性：** 定义能传达同一含义，关键区别有明确依据。
- **一致性：** 定义、约束与可推出的结论相容。
- **可扩展性：** 新概念尽量沿用已有定义，不随意改变旧概念含义。
- **最小编码偏差：** 概念含义尽量独立于字段名、存储格式和编程语言。
- **最小本体承诺：** 只引入满足用途所需的概念与假设，给合理的其他解释留出空间。

这些准则需要结合用途权衡，不要求逐项打分。五项准则见 [Toward Principles for the Design of Ontologies Used for Knowledge Sharing](https://tomgruber.org/writing/onto-design.pdf)；它们与原材料引用的 *A Translation Approach to Portable Ontology Specifications* 是不同论文。

## 落到 TypeScript 与 SQL

以下是工程映射建议。类型声明只能表达部分领域语义，约束要落实到实际数据入口与写入路径。

| 需要表达的含义 | 可选实现与判断依据 |
| --- | --- |
| 对象及属性 | 用 `interface` / `type` 表达结构；概念定义说明字段的业务含义 |
| 真正的子类 | 可用 `extends` 表达结构特化；依据语义上的包含关系选择，不按字段重合比例判断 |
| 互斥变体 | 用带 `kind` 等字面量标记的判别联合；普通 `A \| B` 本身不保证互斥 |
| 可并存的角色或特征 | 用角色集合、对象组合或兼容的交叉类型；`A & B` 表示同时满足两种类型，不自动表达“拥有”关系 |
| 对象关系 | 独立身份、独立生命周期的对象通常用 ID / 外键；归属于主体的值对象可嵌入；多对多关系通常用关联表 |
| 必填与基数 | 分别定义字段存在、非空字符串、非空集合和关联数量；`T[]` 允许空数组，`NOT NULL` 不保证关联数量 |
| 有限取值与数值范围 | 编译期类型配合运行时校验；持久化约束按数据库能力落实为 `CHECK`、唯一约束或外键等 |
| 反向关系 | 优先从同一份关联数据查询；双向保存时明确一致性维护责任 |
| 传递关系与推理 | 递归类型仅描述结构；祖先查询等需要查询或规则实现 |

TypeScript 语法依据：[对象类型、接口扩展与交叉类型](https://www.typescriptlang.org/docs/handbook/2/objects.html)、[判别联合与穷尽检查](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions)。存储选择属于工程判断，按项目已有栈实施。

TypeScript 检查、运行时校验和数据库约束应保持相同业务含义。例如规定数值位于某个区间时，要明确真正执行该限制的层；branded type 不会自行检查运行时数值。复用现有校验工具，无需为套用本方法新增依赖。

## 一个小例子

目标：管理项目成员，并回答“某人在某个项目中承担什么角色”“同一人能否参与多个项目”。

- 概念：`Person`、`Project`，以及连接两者的 `Membership`。
- 关系：一个人可参与多个项目，一个项目可有多人；角色属于某次成员关系。
- 约束：若业务规定每人每项目只有一条当前成员记录，则对 `(personId, projectId)` 保持唯一；一条记录可以有多个角色。
- 实例：同一个人在项目甲担任负责人，在项目乙担任评审。这个实例支持把角色放在成员关系上；把角色直接设为人的全局类型会丢失项目语境。

先做到这些问题可回答。只有需要历史任职查询时，再引入成员关系的有效期及其约束。

## 可直接使用的提示词

```text
我想建模的领域是：【领域】。
用途和现有材料是：【要支持的决策、查询或系统；已有术语、代码、表结构或案例】。

请用本体工程方法，按上面的七步流程整理出满足用途的最小模型。
先从模型必须回答的问题确定范围，再说明概念、属性、关系和约束。
优先复用已有定义，区分类别、实例、角色和状态，显式标记未确认的假设。
用真实案例及合法反例检验模型；遇到冲突，指出需要修订的数据、定义或范围。
需要工程落地时，再映射到当前项目的类型、校验和存储方案。

输出：范围与能力问题、核心概念表、关系与约束、实例验证结果、仍待确认的问题。
每个新增概念说明它支持什么问题；关系复杂时配图，简单时直接用表或文字。
```

整理依据：用户提供的《Ontology Engineering for TypeScript》，以及上文引用的本体工程原始资料。
