# PR 与工作复盘的变化说明

面向没有参与过程的读者，说明哪个对象发生了什么变化、为什么这样做，以及现在能够完成什么。本文用于 PR 和工作复盘中的成果主题；文档结构、来源和发布状态仍由对应领域 Skill 决定。

## 从材料形成主题

- **以实际基线确认变化。** PR 使用完整目标分支差异，复盘使用期初状态和周期内证据；据此区分新增、调整、重构、修复与移除。基线已经存在的能力，只写本次扩展。提交时间、worktree 和对话用于找回线索，最终内容回到实际差异与证据。
- **按职责和能力组织。** 同一能力所需的执行、通信、状态反馈及恢复机制放在同一主题内；有独立目的、使用者或职责的内容分别说明。主题由当前系统的职责与实际变化决定。
- **主题之下保留独立变化。** 每个分点表达一项可理解的变化；重构、功能新增、行为调整可以出现在同一主题中。文件移动、脚本和测试跟随所属能力说明；跨模块且有独立目的的基础设施调整可以单列。
- **用来源找遗漏。** 对大范围改动，内部维护“主题—变化—依据”的简短对应关系，用它核对独立能力、操作入口和重要设计是否遗漏。正文按最终主题成文，提交数量、文件数量和时间顺序不决定篇幅。

主题合并的依据是读者需要一起理解这些变化。例如，后台执行、状态查询、取消及失败重试共同构成导出任务管理能力。共享执行机制与某个业务应用的报表规则，可以分别讲清。

## 主题与分点如何成文

主题开头用一两句话说明改动对象、目的或总体能力；下面按需要分点，把具体动作、决定行为的机制和直接效果连接起来。

```markdown
- **<主题：对象与变化>**。<原有问题或目标，以及本次带来的直接能力>。

  - **<具体变化>**：<谁在什么条件下如何执行>，<因此可以完成什么>。
  - **<配套机制>**：<投递、状态、失败处理等关键规则>，<解决哪个使用问题>。
```

这是多主题 PR 的参考形态。简单修复用一两句话就可以说明。复盘可以自然写成段落，结构随材料和读者需要调整；目的已在主题开头说清时，各分点直接推进新信息。

保留会改变理解的细节：操作主体、作用范围、生效时机、可见反馈，以及取消、失败或恢复后的状态。删去这些条件会把能力写大时，必须留下；类名、文件名和目录只在帮助说明职责或审阅位置时出现。

“重构文件组织”需要进一步说明职责从哪里移到哪里、接口或调用方式怎样变化，以及维护者因此能在哪里修改业务规则。“支持某功能”需要交代功能如何使用、哪些配套机制使它能够持续工作。

## 初衷、能力与效果

| 证据支持的内容 | 适合的表达 |
| --- | --- |
| 明确的需求或原有问题 | “为使用户离开页面后仍能继续导出……”；动机应来自需求或本人说明 |
| 实现已提供的能力 | “导出请求进入后台队列，用户可以关闭页面并在稍后查看结果” |
| 实际观察或测量结果 | 写清观察对象、条件、变化及来源；性能结论需要可比基线 |

实现机制能够支持“现在可以做什么”。“已显著提升效率”“减少了多少返工”等结果需要实际证据。尚无测量时，写清直接能力或预期用途即可；同样要保留效果说明，不能只剩实现细节。

## 虚构 PR 的写法示例

以下以虚构的报表导出系统说明写法。假设基线已有共享执行器和业务模块，但导出依赖页面等待，格式规则集中在共享执行器中；本次改动增加后台任务和进度界面，并移交格式规则。示例中的行为均为设定，实际写作仍以对应仓库差异和验收材料为依据。

### 后台导出

**后台导出与任务管理。** 用户提交导出后可以继续浏览页面，也能在稍后查看任务结果。

- 服务端保存导出条件并返回任务编号，工作进程从队列领取任务，执行过程不再依赖浏览器持续连接。
- 任务依次显示排队、执行中和完成或失败状态；完成后提供下载入口，失败时保留导出条件，用户可以据此创建重试任务。
- 用户可以取消尚未开始的任务；已经执行的任务继续处理，界面显示当前状态。

这里的取消范围是“尚未开始的任务”，不能扩写成可以中断所有导出。

### 导出进度界面

**进度展示与重新进入。** 用户能判断导出是否完成，离开页面后仍能找回任务。

- 任务列表展示服务端返回的状态、创建时间和报表类型，用户可以定位此前发起的任务。
- 进度使用已完成批次与总批次数表示；总数尚未确定时只显示执行状态，避免给出无依据的百分比。
- 再次打开任务页时读取服务端保存的结果，完成后显示下载入口，失败后显示原因与重试操作。

### 架构与源码重构

**分离执行调度与报表格式。** 共享执行器负责领取和运行任务，业务模块维护各类报表的字段与格式。

- 将字段选择和列格式从共享执行器移到现有业务模块，通过已有的报表类型注册入口调用；调整某类报表时，维护者可以在对应模块内完成修改。
- 共享执行器保留队列领取、状态更新和错误记录，所有报表沿用同一套运行过程。

设定的基线已有执行器和业务模块，因此这里说明职责转移，不能写成从零新建架构分层。

## 用到复盘时

工作主题从期初问题讲到判断、行动、结果与当前状态。保留能解释选择和结果的关键机制，并说明尚未解决的约束。个人动机、感受和取舍来自本人陈述；计划、代码完成、合入、部署与使用效果按各自证据表达。

沿用上面的虚构案例，工作主题可以写成：“本期将报表导出改为后台任务，并补充状态查询、排队取消及失败重试。用户可以离开页面后再取回结果，也能判断任务停在哪个阶段。”后面按当期证据补充实际使用结果、交付状态或待解决问题，避免凭功能存在推断效率已经提高。

周期复盘沿用既有来源范围、主体归因和状态规则；常规测试通过及数量仅供内部验收。生活经历和个人思考按其自身意义表达，无需套用工作成果结构。
